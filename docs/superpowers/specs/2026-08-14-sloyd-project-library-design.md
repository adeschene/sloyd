# The project library — design

Multiple projects resident in the browser, each in its own storage slot. A
dropdown off the toolbar's project name lists them; picking one switches to it
instantly, **+ New project** makes another, and every project keeps autosaving
independently. Files stay exactly what they are today — export for backup and
transport — but they stop being the only way to have a second project.

Opened 2026-08-14 by the user: *"There doesn't seem to be a clear way to store,
switch, or create new projects."* That is an accurate reading of the app. This
round makes it false.

---

## 1. The problem

Sloyd today has exactly one project, and nothing says so.

`createDocument()` runs at store construction, `App` restores
`sloyd.autosave.v1` over it on boot, and that single key is the whole of the
user's persistent state. There is no **New**: the only way to start a second
project is to delete every board in the first one, or to export it, empty it and
hope you remember which file was which. There is no **switch**: Import replaces
what is on screen, warns you it is doing so, and leaves the outgoing project
recoverable only if you exported it first. And there is no **list**, so nothing
in the interface ever indicates that "the project" is a thing there could be
more than one of.

For an app whose domain is *shop projects* — things you build one after another,
and come back to when you build the second one like it — a single slot is the
wrong number.

The seam anticipated this. `StorageAdapter` already declares `listRecent()` and
a `capabilities.recentFiles` flag, and the browser adapter answers `[]` and
`false` to both. This round is largely the work of making those honest.

---

## 2. Storage layout, and a second thing to version

Three kinds of key live under the seam:

```
sloyd.library.v1     { layout: 1, activeId, projects: [ ProjectEntry, ... ] }
sloyd.project.<id>   one SloydDocument, exactly as autosave writes one today
sloyd.autosave.v1    the current single slot — read once, then never again
```

`ProjectEntry` is `{ id, name, savedAt, createdAt }`. It is index metadata, not
document data: `name` mirrors `doc.name` so the list can render without parsing
every project, and `savedAt` is what the list sorts on.

This introduces a concept the codebase does not have. `migrateDocument` versions
the **document**; nothing versions the **arrangement of keys the documents sit
in**, because until now there was one key and no arrangement. `layout: 1` in the
index is that version, and it stays deliberately separate from
`CURRENT_VERSION`: a document is still a document, a `.sloyd` file written by
this build is byte-identical to one written by the last, and the two things
version on their own schedules because they change for unrelated reasons.

### 2.1 Identity: the id lives in the index, not the document

A project needs an identity that survives renaming, and `SloydDocument` has a
`name` and no `id`. Keying the library by name would break the moment two
projects shared one, which the app cannot prevent and should not try to.

So the id is generated by the library and stored **only in the index**.
`SloydDocument` gains no field and **`CURRENT_VERSION` stays 6.**

That is a deliberate reading of CLAUDE.md's rule that a version bump exists for
the refusal gate at the far end. Check what a lost id actually costs: a `.sloyd`
file carries no id, so importing one into any build produces a *new library
entry*. That is not a wrong number (v5's kerf argument) and it is not silent
data loss (v6's guides argument) — it is the behaviour you would want from an
import anyway. Neither bump argument reaches this field, so no bump. The
consequence worth stating plainly: **rolling back past this round costs
nothing**, which is not true of the last two rounds and is a large part of why
the layout is shaped this way.

### 2.2 Adoption is the highest-stakes part of this feature

Per the deployment rule stated in CLAUDE.md, `sloyd.autosave.v1` **is** the
user's project. Sloyd has no server-side state and nothing to restore from. An
adoption path that orphans that key destroys real work, and the round has no way
to apologise for it.

On boot, when `sloyd.library.v1` is absent:

1. Read `sloyd.autosave.v1`. If missing or unparseable, create a fresh
   `Untitled` project and write a one-entry index. (Corrupt is treated as
   missing, matching `loadAutoSaved`'s existing "start clean rather than block
   the app" behaviour.)
2. Otherwise run it through `migrateDocument`, mint an id, and write
   `sloyd.project.<id>`.
3. Read that key back and confirm it parses before writing the index. **Write
   new, verify, then commit the index** — never overwrite in place.
4. Write the index with that project active.

**The old key is never deleted.** It costs a few kilobytes and it is the entire
rollback story: a build from before this round finds `sloyd.autosave.v1` exactly
as it left it, because after step 4 nothing ever writes to it again. Deleting it
to be tidy would convert a free rollback into an unrecoverable one, so the
adapter carries a comment saying so at the point where deleting it would be
natural.

If step 3 fails — the new key does not read back — the index is not written and
the old key stays authoritative: the session runs on the legacy single-slot
path, the caret button is not rendered, and `available` reflects whatever the
storage layer reports (a failed write is usually a full quota, which the
existing banner already explains). Adoption is retried on the next boot, since
the absent index is the only thing that triggers it. **A failed adoption must
degrade to *today's app*, not to an empty one.**

**Adoption fires on exactly one condition: `sloyd.library.v1` is ABSENT.**
Nothing else may trigger it — in particular, a *present but unusable* index
must never be treated as an absent one, because that silently clobbers real
project data with a fresh single-entry index built from the stale legacy
document. The document layer already refuses a `version` it doesn't
understand rather than guessing at it (the reason for the v6 bump); the
storage layer owes the same refusal to a `layout` it doesn't understand. Four
cases, and only the first adopts:

- **Key absent.** Adopt, exactly as steps 1–4 above.
- **Key present but `parseIndex` returns null** — corrupt JSON, or a `layout`
  this build does not recognise (in particular a *newer* layout than
  `LAYOUT_VERSION`). Write nothing. Return the legacy document read-only
  (`libraryAvailable: false`). This is a refusal, not a recovery: a future
  build's projects must not be silently discarded because this build can't
  read the index that names them.
- **Index parses, `activeId` names a project whose key is missing.** Fall back
  to the most recently saved project that *is* loadable — never re-adopt the
  legacy key here, since adoption already happened once and the legacy
  document is now stale by definition.
- **Index parses with `projects: []`.** Create a fresh `Untitled` project and
  add it to the existing (empty) index. Still never re-adopt the legacy key —
  same reasoning as above.

## 3. The switch, and a data-loss race that must not be timed around

`App.tsx`'s autosave effect debounces 600 ms on `doc`:

```ts
useEffect(() => {
  if (!restored.current) return;
  setSaving(true);
  const t = setTimeout(async () => { await storage.autoSave(doc); ... }, 600);
  return () => clearTimeout(t);
}, [doc]);
```

If the active project id lived inside the adapter, a timer armed while project A
was open would fire *after* a switch and write **A's document into B's slot**.
That is real, silent data loss: no error, no visual difference, and B's work
gone on the next read.

So the id is an explicit argument — **`autoSave(id, doc)`** — captured in the
same effect closure as the document, with `activeId` joining the dependency
array. A switch changes both in one render, and the effect's existing cleanup
clears the pending timer before the new one arms. The race stops being
*possible* rather than being *timed around*, and the signature is what enforces
it: a future edit that drops the id has to delete an argument, not merely forget
an ordering.

`loadAutoSaved()` gains the same treatment as `loadProject(id)`. The old
single-slot methods stay on the interface only as long as the adoption path
needs them.

### 3.1 Switching routes through `replaceDocument`

Invariant 24 names this feature before it exists: *"A future action that
rewrites `doc.boards` wholesale joins this list"* — the list of things that must
drop every held point, because a grab, a tape anchor and a tape hover all hold
captured world positions whose owning boards may not exist in the new document
at all.

`replaceDocument` already does all of that. So a switch **is** a
`replaceDocument` call, not a new store action. Writing a `switchProject` action
that touches `doc` directly would mean re-deriving invariant 24's three clearing
reasons from scratch and would be the exact shape of edit that invariant warns
about. The store learns nothing new about projects; the library hands it a
document and it replaces one.

Every switch is therefore a load path, and runs through `migrateDocument` — which
is also where invariant 8's board-name uniqueness is enforced, so a hand-edited
project in the library cannot smuggle duplicate names in through the side door.

### 3.2 No confirm on New or switch, and Import's confirm retires

`FileMenu`'s Import currently guards with
`window.confirm('Opening a project replaces what is on screen. Continue?')` when
`doc.boards.length > 0`. That prompt exists because the outgoing document was
about to be destroyed.

Once every project autosaves to its own slot, nothing is destroyed by opening
another one, and the prompt would be asking permission for something that no
longer happens. Import lands in the library as a new entry and switches to it;
New creates a slot and switches to it; picking a row switches to it. **None of
the three prompts.** This is stated as a decision rather than left implicit,
because inheriting the confirm by analogy is the obvious thing to do and would
be wrong.

## 4. The dropdown

The toolbar's project name is an editable `<input class="input doc-name">` and
**stays one.** Renaming a project is what that field is for, and converting it
into a menu trigger would trade a working affordance for a new one. The menu
hangs off a caret button beside it:

```
[ Workbench          ][▾]  Add board   Cut list   …
                      ┌──────────────────────────────────┐
                      │ ● Workbench        2 min ago     │
                      │   Shaker end table  yesterday ⧉ ×│
                      │   Tool cabinet      3 days ago   │
                      ├──────────────────────────────────┤
                      │ + New project                    │
                      │ ⬆ Import…                        │
                      └──────────────────────────────────┘
```

Each row carries a status dot for the active project, the name, a relative
timestamp, and duplicate (`⧉`) and delete (`×`) controls revealed on hover **and
on keyboard focus** — hover alone would make both operations unreachable without
a pointer.

**Import moves into the menu; Export stays in the toolbar.** Import now creates
a library entry, which makes it a project-creation action and puts it beside
**+ New project**. Export acts on the document currently open and belongs where
it is. `FileMenu` keeps owning both handlers and their error surface — only
Import's trigger relocates, and its confirm is deleted (§3.2).

**Rows sort by last saved, not last opened.** The option the user picked said
"last-opened"; this is a deliberate narrowing to the same effect for less
machinery. `savedAt` has to bump on autosave regardless, for the timestamp to be
honest. A separate `openedAt` would differ from it only when you open a project
and change nothing — and in that case "last saved" is arguably the more useful
answer anyway, since it orders by where the work is.

### 4.1 Why the menu's keys do not go through `App`'s keydown effect

Invariant 27 requires every **window-level** shortcut to live in `App`'s single
keydown effect, and any new `window` listener to take the cut-list-open flag
explicitly.

The menu's Escape is bound on the menu subtree, and its outside-click listener
is mounted only while the menu is open. Neither is a window-level shortcut in
invariant 27's sense: they are scoped to a component that exists for as long as
the interaction does. Routing them through `App` would mean threading menu state
up to `App` and re-deriving a `cutListOpen` guard for a menu that cannot be open
behind the cut list anyway — the shell is `inert`, and opening the cut list is
itself a toolbar click that closes the menu.

Recorded here because it looks like an invariant 27 violation and is not, and
the next person to read the file should not have to re-derive that.

## 5. Delete, the one destructive act

Undo is per-document. There is no cross-project undo, and there is no trash. A
deleted project is gone.

Delete is therefore a **two-step inline confirm**: the row's `×` becomes
"Delete?" and a second click commits, with any other interaction reverting it.
Not a `window.confirm` — the app throws exactly one native dialog today and this
round retires it (§3.2), so adding a new one would move against that. Keeping
the confirmation inside the row also keeps the project's name visible while you
confirm, which is the fact you actually need.

Two edge cases, stated rather than discovered later:

- **Deleting the active project** switches to the most recently saved remaining
  one.
- **Deleting the last project** immediately creates a fresh `Untitled` and makes
  it active. There is never a no-project state, so no component has to render
  one.

Duplicate suffixes the name with "copy" and does not enforce uniqueness across
the library. Invariant 8 governs **board** names *inside* a document; projects
are keyed by id and a library that silently renamed your projects would be worse
than two rows both reading "Untitled".

## 6. Testing

This feature never touches the r3f viewport, so the "no unit tests by design"
rule does not apply to any of it. `@testing-library/react` is already in use
(`App.test.tsx`, `Toolbar.test.tsx`) and the DOM surface is testable in full.

**`storage/browser.test.ts` carries the weight** — four adoption cases:

- adoption from a real v1 autosave produces a project whose document round-trips
  equal to the original;
- adoption with the old key absent produces a one-entry library holding
  `Untitled`;
- adoption with the old key corrupt does the same, and does not throw;
- **the old key still holds its original bytes after adoption** — the assertion
  that keeps the rollback story true, and the one a tidying pass would delete.

**A named test for the switch race.** Arm the debounce with project A's
document, switch to B, let the timer fire, and assert B's slot does not contain
A's document. That bug is invisible in every screenshot and survives any amount
of manual clicking; the test is the only thing that fails when the id stops
being an explicit argument.

**`App.test.tsx`** covers new / switch / delete / duplicate / import through the
real DOM, including that deleting the last project leaves a usable app.

## 7. Verification and deployment

Production is verified by page load only, per the deployment rule — and this
round needs that rule held **harder** than usual, not more loosely. The adoption
path reads and acts on the verifying browser's real `sloyd.autosave.v1`; loading
production once is enough to run it. So adoption is exercised **against the dev
server with a hand-seeded legacy key**, in every one of its four cases, and
production gets a page load and a bundle-hash check and nothing else.

Rollback costs nothing at the document level (§2.1) and nothing at the storage
level (§2.2): a pre-round build reads `sloyd.autosave.v1`, which is still there
and still correct. The one thing rollback loses is any project created *after*
adoption — those live in `sloyd.project.<id>` keys the old build cannot see.
Export before rolling back, as always.
